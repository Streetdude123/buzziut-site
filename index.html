gifting system, server side

you can buy a product for another player and it goes to their inbox, even if they're in another server or offline. if they don't claim it before it expires it goes back to whoever sent it.

  • ReceiptLedger.luau↗Roblox keeps calling ProcessReceipt until it gets an answer, so every PurchaseId gets recorded and one purchase can never be granted twice.
  • InboxStore.luau↗every write is an UpdateAsync, so two servers editing the same inbox can't duplicate or lose a gift and a double click can't claim it twice.
  • Gift.luau↗the gift data and the payload the client gets, with the ids the client shouldn't see taken out. returned gifts never expire again so they can't bounce back and forth forever.
  • Store.luau↗the DataStore wrapper that every write goes through, it retries with backoff.

Untitled Tower Defense

live on Roblox roblox.com/games/119472908687736 ↗

a full tower defense game I made by myself, that includes the code, UI, enemy behaviour, economy, balance and mobile support. it's live right now so you can go play it and check everything below yourself.

hexagon stat radar
it reads each unit's stat table and draws the polygon, the axis web and the letter grades at runtime. I drew it with primitives myself and didn't use a charting module, so adding a new unit doesn't need any UI changes.
wave and enemy director
later waves bring tougher mixes of enemies, enemies move in different ways, and the multi phase bosses change their attack patterns in the middle of the fight.
tower placement
validation so the preview always matches the placement you actually commit. it works the same with mouse and touch.
economy and support units
income towers and payouts every wave, with some anti snowball limits so a really strong early game doesn't make the rest of the run boring.
loadout system
equip, unequip and reorder. that includes handling sparse arrays, which break Lua table iteration without any error if you aren't careful.
responsive UI and performance
layouts that work on a small phone and on widescreen, animations split between client and server, and the per frame loops merged into as few as I could.

unannounced asymmetric horror project

in development

an asymmetric horror game with 12 survivors against 2 strikers on two maps, kind of like Dead by Daylight. I can't say the name until we announce it. I am the only programmer on it and my partner does the design and the map layouts.

custom character controller
I wrote the movement from scratch because I didn't want the default humanoid feel. sprint, crouch and the state changes between them, with weight based animation crossfading.
soft shift lock camera
a custom camera rig set up for over the shoulder horror framing. the easing keeps your aim responsive and gets rid of the stiff feel the default shift lock has.
striker AI
PathfindingService routing that recomputes when a path fails, all running off a stamina model. when the striker gets exhausted it drops to walk speed, and a re-engage threshold decides when it starts chasing again.
objectives and interaction
proximity prompts where every objective keeps its own state and feeds into the round's win conditions.
server authoritative movement
the server validates walk speed, position and player state, which stops exploiters from editing their client to outrun you or clip through the map.

how I work

  1. scopeyou tell me the system or the bug. I ask the questions that change the estimate, then I write down what is included and what isn't.
  2. estimateyou get a fixed deliverable and a timeline before I start anything. if the job grows halfway through we re-quote it before I do the extra work.
  3. buildI send updates as I go and each one has something in it you can test.
  4. handoffyou get commented, modular code that drops straight into your place and a quick walkthrough of how it fits together. for a while after that I fix anything that comes up.
